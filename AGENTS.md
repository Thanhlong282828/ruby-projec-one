# Ruby HRM development conventions

- All features belong to a local Rails Engine under modules/. Keep MVC in app/ and layered Ruby code under lib/hrm_<module>/{application,domain,infrastructure,providers}/.
- Application Queries read data; Application Commands perform mutations and orchestration. Domain Services contain business rules. Infrastructure Persistence implements Domain repository interfaces with Active Record.
- Providers own bindings. Resolve repository contracts through Hrm::Container in constructor defaults; permit explicit constructor injection for tests. Store constant names in the registry so Rails reloads do not retain old class instances. Never bypass a missing binding with an implicit fallback.
- Controllers coordinate requests, authorization, use cases and responses. They may instantiate unsaved form models, but must not issue database queries or persist records. Views render prepared data; model associations/validation remain ordinary Active Record responsibilities.
- User-driven reads preserve Pundit scope. Commands enforce actor authorization even when invoked outside HTTP. Trusted scheduler/CLI entrypoints must remain separate from public HTTP actions.
- Preserve encryption, optimistic locking, audit/outbox atomicity, ownership rules, existing route helpers and business behavior unless the task explicitly changes them.
- Declare HTTP routes individually with get/post/patch/put/delete; no resource/resources/namespace shorthand in route files.
- Run ruby bin/check-routes, ruby bin/check-architecture, bin/test-docker and Rails zeitwerk:check for relevant architecture changes. Scan all engines using bundle exec ruby bin/brakeman --no-pager.
- Database-changing tests must use RAILS_ENV=test and hrm_test. Do not reset development data or copy database/secrets from the Laravel reference.
- Desktop/laraveldji/admin is a read-only architecture reference for this Rails project. Do not modify it or claim feature parity with its multi-company HRM.
- Keep HUONG_DAN_LARAVEL_SANG_RAILS.txt aligned with actual paths and explain new terms for someone moving from Laravel. Distinguish Application Commands from terminal/Artisan-style commands.

- Company/RBAC authorization is persisted in MySQL: company_roles, permissions, role_permissions, user_permissions. Defaults in PermissionCatalog are provisioning only; do not use a role enum or wildcard admin bypass as the runtime permission source.
- Custom roles are company-scoped database rows. Preserve users(company_id, role) -> company_roles(company_id, key) and same-company composite foreign keys. Tenant identity comes from the authenticated account, never a client-selected company_id/header.
- User grants/denies, role edits and account administration must authorize the actor, scope target IDs to actor.company_id, preserve protected admin recovery and write audit in the same transaction.
- Scope auxiliary reads too: form options, payroll snapshots, dashboard cache, audit, outbox metadata, scheduled summaries, decision mail and Action Cable streams. Permission revocation must affect existing credentials/subscriptions.

## Mandatory security rules — áp dụng cho mọi thay đổi

- Security là tiêu chí thiết kế và nghiệm thu bắt buộc cho mọi module, web/API, job, scheduler và CLI. Trước khi sửa phải đọc AGENTS.md, xác định dữ liệu nhạy cảm, entrypoints, quyền và company scope bị ảnh hưởng; kiểm chứng code/config thực tế, không lấy báo cáo PASS cũ làm bằng chứng cho thay đổi mới.
- Giữ Module + MVC + CQRS khi triển khai bảo mật: controller điều phối, Request allowlist input, Query/Repository lọc dữ liệu và Command kiểm quyền trước mutation. Provider chỉ bind dependency; không thay thế Policy hoặc tenant scope. Mặc định từ chối, không thêm admin bypass hay tin role/company từ client.
- Không làm yếu authentication, authorization, CSRF, encryption, TLS, CSP/security headers, rate limit hoặc audit để sửa lỗi hay làm test đạt. Xác định và sửa nguyên nhân; không thêm ignore/baseline hay xóa assertion để che lỗi bảo mật.
- Web authentication phải dùng credential ngẫu nhiên có thể thu hồi phía server, chỉ lưu digest trong MySQL; cookie mã hóa có HttpOnly, SameSite và Secure khi production. Kiểm expiry tuyệt đối và account/company active trên server; không quay lại xác thực chỉ bằng session user_id. Không lưu raw token/password trong DB, log, URL hoặc audit/outbox.
- Logout phải thu hồi phiên hiện tại. Đổi mật khẩu/disable account phải thu hồi web/API credentials trong cùng transaction; cấp credential phải đồng bộ với thay đổi mật khẩu bằng row lock và kiểm lại trạng thái. Các tác vụ SQL trực tiếp phải thực hiện tương đương vì callback Active Record có thể bị bypass. Không tự hồi sinh credential đã thu hồi.
- WebSocket phải xác thực phiên, kiểm origin và company stream; kiểm lại phiên/quyền trước truyền dữ liệu cho subscription đang tồn tại. API Bearer token không được tự động thay bằng session cookie. Thu quyền phải tác động tới credential/subscription đã cấp.
- Bảo vệ endpoint đăng nhập bằng rate limit dùng store chia sẻ giữa các instance, theo IP và tài khoản đã normalize thống nhất với authentication. Kiểm cả form/JSON, format suffix, path escaping và slash normalization; trả lỗi chung và 429/Retry-After phù hợp. Không ghi email nguyên văn vào throttle key. Ghi rõ trade-off lockout và yêu cầu proxy xử lý header chống spoof.
- Validate kiểu, độ dài, định dạng và nghiệp vụ; chỉ mass-assign trường được phép. Dùng SQL parameter binding, không nội suy input vào SQL/Arel.sql, shell hoặc dynamic constant/class lookup. Không dùng html_safe/raw cho nội dung không tin cậy. Giữ CSRF trên web và hạn chế CORS/origin theo nhu cầu thực tế.
- Bảo vệ dữ liệu nhân sự, lương, ngân hàng và định danh ở cả response, export, cache, log, mail, audit và event. Response nhạy cảm phải no-store; filter thông tin nhạy cảm trước logging. Export phải có authorization và tenant scope, chống spreadsheet formula injection khi dữ liệu mở bằng spreadsheet. Upload, webhook hoặc gọi URL bên ngoài mới phải kiểm soát quyền, kích thước/loại nội dung, đích truy cập, timeout và tính xác thực phù hợp; không tin tên file, Content-Type hay URL do client tự khai.
- Dùng transaction/row lock, unique/composite FK/CHECK và idempotency phù hợp để bảo vệ tranh chấp, liên kết chéo company và tác vụ tài chính. Không bỏ database constraint hoặc ghi ngoài command để né quy tắc nghiệp vụ; nêu rõ các đường ghi đặc quyền có thể bypass validation/callback.
- Secrets, private keys, .env thật và backup chứa dữ liệu không được commit, đưa vào image hoặc gửi ra ngoài phạm vi được phép. Dùng secret riêng từng môi trường, không mang mật khẩu local/demo lên production. Runtime container chạy non-root; production cần TLS, host/origin allowlist, network exposure tối thiểu và quyền DB tối thiểu, tách quyền migration khi triển khai.
- Kiểm dependency advisory bằng `bundle exec bundler-audit check --update`; áp dụng bản vá tương thích, giữ lockfile và nền tảng được hỗ trợ. Duy trì CI và cấu hình cập nhật dependency; không coi có file cấu hình là remote CI/Dependabot đã chạy. Không tự publish, deploy hay đổi thông tin xác thực ngoài phạm vi được giao.
- Thay đổi authentication/permission/tenant, input, truy vấn, cache/export, realtime hoặc tích hợp bên ngoài phải có regression test phù hợp cho đường thành công và đường bị từ chối: unauthenticated, quyền bị thu hồi, cross-company/IDOR, malformed input và replay/race khi liên quan. Kiểm CSRF/rate limit bằng test bật bảo vệ thật, không chỉ dựa test environment vốn tắt middleware.
- Trước khi kết luận thay đổi code liên quan bảo mật hoàn tất: chạy test liên quan trên hrm_test, các architecture/route/zeitwerk gates phù hợp, Brakeman toàn engines và dependency audit. Chạy toàn bộ test khi ảnh hưởng nền dùng chung/authentication. Không reset development; sao lưu trước migration có tác động DB local và bảo vệ file backup. Sửa thuần tài liệu không cần chạy lại toàn bộ test ứng dụng.
- Báo cáo trung thực các gate đã chạy, advisory còn lại, phạm vi chưa kiểm, rủi ro và giới hạn triển khai. Scanner không thay thế kiểm thử nghiệp vụ, threat review hoặc pentest; không tuyên bố “chống hack tuyệt đối”. Kết quả từng lượt lưu trong evidence/report, không ghi status tạm thời hoặc số test vào phần luật lâu dài.

## ERP workspace conventions

- Group related business screens under primary menus; use the same permission-filtered navigation catalog for sidebar and Dashboard Board. Every visible menu must resolve to a working authorized page. Never advertise empty modules as completed DJI parity.
- Every KPI/metric card must link to its actual source list/report with matching scope and filters. Label count population and cache freshness; distinguish zero data from missing/forbidden functionality.
- Keep application onboarding guidance separate from employee onboarding business cases. Port DJI state machines and prerequisites explicitly; document missing recruitment/provisioning integrations before claiming completion.
- Signed webhook contracts bind timestamp and raw body; validate freshness, body size/type, schema and constant-time signature. Durable idempotency must reject conflicting reuse of an event ID. Retry with a fresh signature and preserve event identity. Trusted internal receiver is not a public integration management platform; never accept arbitrary user-controlled outbound URLs without SSRF protection.

## Environment parity and secret-safe auditing

- Include .env/example declarations and config/source consumers when comparing DJI features. Variable presence, source reference, configured driver and verified runtime capability are distinct; do not infer external integration activation from a declared key.
- ENV audit artifacts may contain names, file/line references and semantic mappings only. Never load/evaluate source .env files or export values, value hashes, secret fragments, credentials or signed URLs. Handle quoted multiline values without interpreting their contents as new key declarations.
- Keep DJI read-only and do not transplant its keys/credentials, switch production providers, rotate live encryption keys or enable external security controls as part of a local comparison. Add a variable only alongside real configuration consumption and tested behavior; placeholder variables are not feature parity.

## Inbound integration boundaries

- Public machine webhook ingress authenticates its connection using HMAC, never browser sessions or a client-selected company. Serialize verification/reception with connection disable/key rotation; derive tenant from the verified connection.
- Cap and isolate raw body processing before automatic Rails parameter parsing/logging. Bound payload bytes, UTF-8, JSON schema/depth and header formats; compare HMAC in constant time; use durable case-sensitive event identity plus payload digest for duplicate/conflict handling.
- Per-connection signing keys and incoming payload/review notes must remain encrypted at rest. Return a new key only from authorized create/rotation responses; normal JSON/metadata pages must omit secret/body fields. Sensitive payload reads require their own revocable permission.
- A receipt acknowledgment is not business approval or automatic application. Do not dispatch untrusted inbound data into HR/payroll/finance or grant account access without an explicit adapter, permission scope, transaction/idempotency contract and tests. User-session revocation and machine-connection revocation are distinct and must be documented.

- Engines publishing restricted realtime event metadata must register prefix-to-permission mappings with string names. Check these grants before every transmit on existing subscriptions; a generic realtime.read grant must not bypass a module's metadata authorization. Never broadcast raw integration payloads or credentials.

## Outbound delivery boundaries

- Durable MySQL delivery rows are the source of truth; scheduler/Redis handoff must be recoverable. Preserve immutable event identity/body, idempotency conflict checks and attempt journal across retry/replay. Enforce bounded attempts/replays and optimistic replay versions.
- Before network I/O, recheck requester grants/company/account and connection status. Never put credentials/payload into Redis arguments, audit or realtime. Register outbound delivery/attempt event prefixes as restricted Integration metadata.
- Outbound destinations must be operator-controlled allowlist entries; no arbitrary client URL. Enforce HTTPS with peer/hostname verification, public-address DNS validation and pinning, no redirects/proxy, bounded connect/read/write/total time and bounded discarded response. Keep local targets disabled unless deliberately configured.
- Database locks cannot guarantee exactly-once delivery across a remote HTTP/DB commit crash window. Document receiver Event ID deduplication as a requirement; preserve retries rather than claiming remote business completion from a 2xx.

## Integration audit projections

- Module audit portals must authorize a dedicated company-scoped permission, whitelist record types/actions and project metadata explicitly. Never serialize arbitrary audit metadata, credentials, raw payloads or actor contact details into the portal/API. Broad global audit access and module-specific portal access are distinct grants.
- Bound date windows and validate every filter type. Use keyset pagination for growing logs; preserve period/resource/record filters in every KPI and cursor link. Resolve source links in bounded batches through tenant-scoped queries; deleted sources retain history without a broken source link.
- When reloading the development web server, target the observed long-lived web container/process explicitly. Do not send a service-wide signal while one-off tests, migrations or scanners are running. Keep the existing container used by VS Code.

## Payroll artifact boundaries

- Generate payroll artifacts only from authorized same-company finalized sources, never client-provided amounts/files. Bound rows/bytes and capture a stable source snapshot with locks; preserve artifact identity and idempotency. Keep financial units explicit and consistent with the current data contract, never infer a new scaling rule from a legacy column name.
- Encrypt stored artifacts, project metadata without decrypting file bytes, and require a separate revocable download grant. Validate checksum/size/schema/identity before serving; commit safe access audit/outbox before returning bytes, including integrity-failure evidence. Avoid public filesystem exposure and spreadsheet formula injection.
- Realtime permission lists are conjunctive nonempty arrays of names; malformed lists fail closed. Sidebar/Board entries requiring several source grants must use explicit all-grants matching, not the default any-grant behavior.
- A payroll outbound bridge must bind the actual immutable source, reserve its typed event contract and recheck source/company grants in the worker. Generic integration.send is not permission to disclose salary artifacts; reconciliation CSV is not an accounting/provider/statutory export.

- Generic outbound enqueue/replay/worker must share bounded UTF-8/schema validation and reserve server-owned payroll/erp/government event roots for separate source-bound bridge contracts. Worker/replay compare persisted digest with decrypted bytes before network/signing; never silently normalize bytes. Corrupt payloads fail closed without a fabricated HTTP attempt. A status-only quarantine may skip decrypting validators only on a locked record with exactly the status mutation, retaining optimistic locking, DB constraints and atomic audit/outbox. Metadata projections must not decrypt payload just to exclude it later.

- Source-bound notifications must distinguish descriptor disclosure from artifact transfer. Preserve composite source ownership, server-generated typed body/key, and separate revocable source-notify/read grants; generic input must not occupy typed event/key namespaces. Acquire all contended locks before consistent grant reads under MySQL REPEATABLE READ and bypass query cache for authorization under those locks. Realtime source guards must resolve trusted same-company/type OutboxEvent IDs through current scoped sources, retaining only registered class names. Never accept a guard class name from a request.

## Installation identities and company memberships

- A root login identity may own several company User profiles; membership profiles never own password digests. Keep identity/company immutable, composite business FKs intact and database insert/update guards active. Never flip actor.company_id to switch context or copy password/role grants across companies.
- Installation-wide SystemGrant permissions are distinct from company roles/overrides; ordinary company administration cannot manufacture them. Every context switch must bind the actual authenticated session/token to its principal, lock/recheck assigned active profile, preserve absolute expiry and emit audit/outbox. Password changes revoke all principal credentials; profile revocation is local. Existing Cable streams must fail after context changes.
- Canonical schema is structure.sql so MySQL triggers survive fresh database creation. Schema loading must verify expected guards; test helper must fail closed if hrm_test, migration versions or triggers are wrong. Use a short-lived migration-role process, never grant runtime SUPER or relax binary-log trust merely to create triggers.
- Local MySQL TLS preparation targets only this compose service/volume, keeps its existing CA and private keys inside the volume, preserves backup certs and verifies CA/hostname. Never alter another project's MySQL or disable TLS verification as a client compatibility workaround. Production needs its own deployment-specific migration role/CA/secrets.

- Personal credential management is scoped to principal identity ownership, never company-admin authority. Require the actual authenticated caller credential, recheck expiry/profile/context after contended locks, project metadata without digests and commit revocation with audit atomically. Do not broadcast personal session metadata to company subscribers or claim device tracking without collected evidence.

## Gradual static typing and reproducible quality gates

- Keep the typed Payroll command/query path checked through its repository contracts and actual implementation bodies. Do not claim the whole application is strict because the compiler exits successfully. Preserve nil input authorization/validation behavior when adding signatures.
- Prefer real source/API requires over autogenerated unresolved-constant todo stubs. Document casts at Container, framework or JSON boundaries; never add broad T.unsafe/T.untyped, ignores or fake application constants merely to make the gate green. Put reloadable result/type constants in their own Zeitwerk files and test cold loading as well as eager loading.
- Generate/verify Rails DSL RBI only against hrm_test with test environment guards, installed Engines loaded and provider bindings resolved. Serialize generation steps; review generated changes, keep Gemfile.lock/config/RBI together, and verify DSL drift and shim duplication. Do not hand-edit generated RBI to suppress application errors.
- Keep lint, typecheck, explicit routes, architecture, autoload, security scanners and SQL tests in reproducible local/CI gates. A negative type probe must exercise a real contract and remove its temporary source on exit. Generated dependency RBI may be excluded from formatting only, not from Sorbet verification.
- Secret scanning must redact values and cover publishable source, including untracked changes. Do not copy/read ignored local env/private keys/backups into reports or scan snapshots. Exceptions must match a verified public fixture/example narrowly, with a reason; do not exclude entire engines or dependency trees.
- Check the canonical Dockerfile image without source mounts; only a public CA may be mounted for local test DB verification. Compare packaged application files with source and distinguish local evidence from GitHub checks of a specific committed revision.
