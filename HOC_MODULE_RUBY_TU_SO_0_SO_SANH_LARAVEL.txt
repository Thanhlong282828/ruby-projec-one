 HAI LUỒNG KHÁC NHAU, ĐỪNG TRỘN:
 A. Lúc boot: Gemfile -> Bundler -> hrm_attendance.rb -> Engine -> Provider -> Container có binding.
 B. Lúc có request: Route -> Controller -> Use case -> resolve Repository -> Policy/Scope -> Model -> SQL.
 Provider không chạy như một bước SQL ở mỗi request; container dùng binding đã đăng ký.
 Khởi tạo .new của use case có thể resolve dependency trước khi .call được gọi.

 Ví dụ bạn bấm “Vào ca hôm nay”:
 POST /attendances -> AttendancesController#create -> CheckIn#call
 -> AttendanceCaptureService#check_in -> lấy Employee -> khóa Employee
 -> kiểm trạng thái + trùng ngày -> build Attendance -> authorize create?
 -> save! -> validation -> INSERT MySQL -> callback audit + outbox -> COMMIT -> redirect.

 Ví dụ mở danh sách:
 GET /attendances -> AttendancesController#index -> ListAttendances#call
 -> authorize index? -> repository.list -> policy_scope! -> giới hạn company + chủ sở hữu
 -> includes + order + pagination -> SELECT -> @attendances -> index.html.erb.

 - rescue là TỪ KHÓA bắt exception. Hai nơi dùng tên resolve không có cùng nhiệm vụ.

 Container project nhỏ, không phải sao chép toàn bộ Laravel container:
 - Không tự resolve tùy ý mọi class bằng reflection constructor.
 - Không có đủ scoped/singleton/tagging của Laravel.
 - Bind giữ chuỗi class để reload không giữ class cũ; Mutex bảo vệ registry khi nhiều thread.

 - Engine không isolate_namespace: model như Attendance/User là constant chung, không phải HrmAttendance::Attendance.

 Scope thật:
  return tenant if user&.allowed?("attendance.read_all")
  user&.allowed?("attendance.read") ?
    tenant.joins(:employee).where(employees: { user_id: user.id }) : scope.none

 Nghĩa:

8. CHECK-IN: VÌ SAO CÓ INTERFACE, SERVICE, REPOSITORY VÀ MODEL?
====================================================================================================================
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | LARAVEL / PHP (đối chiếu)                              | RUBY / RAILS TRONG PROJECT                                         |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | Interface: public function save(...);                  | def save!(record:); raise NotImplementedError; end — hợp đồng,     |
 |                                                        | chưa chạm MySQL.                                                   |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | Implementation: Eloquent... implements Interface       | ActiveRecordWriteRepository < WriteRepositoryInterface —           |
 |                                                        | implementation override save!.                                     |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | Service gọi $repo->save($record)                       | @repository.save!(record: record) gọi method của implementation đã |
 |                                                        | inject.                                                            |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | $employee->attendances()->make(...)                    | employee.attendances.new(...): model mới ở RAM, chưa INSERT.       |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | $record->saveOrFail()                                  | record.save!: validation + callbacks + SQL, thất bại ném           |
 |                                                        | exception.                                                         |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | Transaction + lockForUpdate()                          | employee.with_lock do ... end: transaction và row lock; mọi writer |
 |                                                        | liên quan phải tuân cùng chiến lược.                               |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 | DB UNIQUE(employee_id,work_date)                       | Index unique employee_id/work_date chặn trùng cả khi vượt          |
 |                                                        | validation hoặc có request đồng thời.                              |
 +--------------------------------------------------------+--------------------------------------------------------------------+
 Diễn giải service thật:
 1. require_actor!(actor): tài khoản/company/role còn hợp lệ theo DB, không chỉ actor khác nil.
 2. employee_for_user!(user: actor): Employee có company_id và user_id khớp actor; không có -> 404.
 3. with_employee_lock: serialize các thao tác check-in cùng nhân viên.
 4. unless employee.active? || employee.probation?: nhân viên inactive bị chặn.
 5. already_checked_in?: có record ngày đó thì ném InvalidState.
 6. build: gắn employee/company, work_date theo at.to_date, checked_in_at theo at.
 7. authorize!(actor, record, :create?): permission attendance.clock + employee.user_id chính mình + cùng company.
 8. save!: chạy validation. ObservableRecord ghi audit/outbox cùng transaction model.
 9. Block thành công -> commit. Lỗi -> rollback, controller bắt lỗi phù hợp và redirect thông báo.

 Checkout:
 read.find!(actor:,id:) đã scoped -> authorize checkout? -> record.with_lock ->
 update checked_out_at chỉ nếu chưa có. Gửi lại checkout không thay thời gian cũ.
 Tính “idempotent” ở đây là phần update timestamp; không có nghĩa mọi endpoint project đều idempotent.

 Không gọi new ReadRepositoryInterface rồi .list: nó sẽ raise.
 Không copy SQL vào interface. Không nhét permission vào provider.
 Không bỏ model vì “đã có repository”: Active Record model vẫn sở hữu quan hệ/validation/callback.

 Observer chỉ ghi tên trường thay đổi, không dump password/bank/national_id/salary values vào audit.

 Không mọi model đều include ObservableRecord; User quản trị có audit! tường minh tại AdministrationRepository.

 Outbox giao ít nhất một lần, KHÔNG đảm bảo exactly-once:
 HTTP receiver có thể đã nhận nhưng dispatcher crash trước delivered_at -> gửi lại.
 services/event_sink/server.py dùng SQLite riêng chỉ lưu integration event, event id unique + INSERT OR IGNORE.
 HRM nghiệp vụ vẫn MySQL; receiver SQLite không thay database nhân viên.
 HMAC SHA256 X-Event-Signature xác thực body; không phải mã hóa nội dung và không thay HTTPS production.
 Nếu retry sau broadcast/mail enqueue trước delivered_at có thể tạo notification/mail trùng;
 receiver idempotent không tự làm mọi side effect idempotent. Đây là giới hạn cần biết khi nâng cấp.

 | Mailable + Mail::to()->queue()                         | LeaveMailer.decision(...).deliver_later; deliver_now gửi ngay (nếu |
 |                                                        | trong job thì vẫn ở worker).                                       |

 config/sidekiq.yml concurrency 5, queues default/mailers.
 ApplicationJob hiện không tự retry mọi deadlock: dòng retry_on Deadlocked trong đó là comment.

 DailySummaryJob duyệt active companies -> query pending count/recipients cho từng company -> mail.

THỨ TỰ ĐỌC KHI ĐƯỢC GIAO BUG:
1. Từ URL + HTTP method tìm route.
2. Tìm controller/action, before_action và lớp cha.
3. Theo .new.call tới Command/Query, đọc initialize để biết dependencies.
4. Xem Policy/Scope hoặc guard mà nó gọi.
5. Xem contract -> provider -> implementation.
6. Xem Model validations/relations/callback, migration/index/FK.
7. Xem view hoặc JSON serialization.
8. Xem tests gần chức năng và integration cross-company.
9. Có side effects: theo ObservableRecord -> observer/outbox -> job -> mail/channel.
10. Có cache: xem key scope + invalidation; đừng xóa cache để che bug permission.

27. LỘ TRÌNH HỌC CÓ BÀI GIẢI — KHÔNG CHỈ CÂU HỎI PHỎNG VẤN
====================================================================================================================
BUỔI 1 — BIẾT RUBY ĐANG VIẾT GÌ
Mở read_repository_interface.rb chấm công.
Tự đọc to: module là namespace; class là hợp đồng; def list là method;
actor: bắt buộc, page:1 mặc định; raise là chưa triển khai; end đóng phạm vi.
Kết quả cần hiểu: file này không có SQL, không có permission, không có HTML.
Đối chiếu Laravel: interface public function list(User $actor, int $page=1).

BUỔI 2 — TÌM ĐƯỜNG VÀO
Mở attendance route và controller; chỉ theo GET /attendances.
Đáp án: index -> ListAttendances.call -> authorize index? -> repository.list -> Scope -> SQL -> ERB.
Không theo CheckIn nếu đang đọc GET; CheckIn chỉ chạy POST.

BUỔI 3 — BIẾT SQL CHẠY Ở ĐÂU
Mở ActiveRecordReadRepository và Hrm::Pagination.
Đáp án: policy_scope trả relation; includes/order/limit/offset ghép query; to_a nạp record.
Chưa to_a không có nghĩa tuyệt đối mọi method đều lazy: count/exists?/pluck/find cũng thực thi SQL.
So Laravel: Builder khác Collection; Ruby Relation khác Array.

BUỔI 4 — BIẾT QUYỀN VÀ COMPANY
Mở AttendancePolicy + ApplicationPolicy + User.
Đáp án: index? kiểm read/read_all; tenant lọc company;
read_all trong company, read chỉ Employee của user; không có quyền scope.none.
Thử trong test, không sửa SQL production/local thật để “xem có bị chặn không”.

BUỔI 5 — BIẾT SERVICE GHI DỮ LIỆU
Theo POST check-in, đọc từng bước ở phần8.
Đáp án: repository object đã được provider bind; interface không làm save;
model save! thực thi validation + callbacks + SQL; lock/unique chống hai lần.

BUỔI 6 — HỌC LỖI
Tìm rescue trong AttendancesController, rescue_from trong ApplicationController.
Đáp án: InvalidState thông báo nghiệp vụ; RecordInvalid dữ liệu sai; RecordNotUnique race/unique;
NotAuthorized ->403; RecordNotFound ->404; StaleObjectError ->409.
Không rescue StandardError rồi luôn báo thành công.

BUỔI 7 — THÊM MỘT VALIDATION NHỎ TRÊN NHÁNH HỌC RIÊNG
Ví dụ [ĐỀ XUẤT] giới hạn độ dài notes ứng viên bằng model validation, thêm test invalid.
Đáp án nơi sửa: modules/recruitment/app/models/candidate.rb và test module.
Không cần sửa provider/interface nếu không đổi contract.
Học cách test invalid và render422, không chỉ test happy path.

BUỔI 8 — TRANSACTION VÀ LOCK
Đọc ReviewLeave + with_review_lock + LeaveReviewRules.
Đáp án: khóa employee bảo vệ số dư chung giữa nhiều đơn; khóa request bảo vệ trạng thái một đơn;
transaction đảm bảo review và outbox cùng commit. Row lock khác Redis lock, khác optimistic lock.

BUỔI 9 — JOB/MAIL/CACHE/REALTIME
Theo event reviewed -> OutboxDispatchJob -> LeaveDecisionJob -> LeaveMailer.
Đáp án: request không chờ SMTP; worker đọc job Redis; cron outbox mỗi phút;
cache dashboard có company/user/quyền; realtime chỉ báo có dữ liệu mới.

BUỔI 10 — GIẢI THÍCH KIẾN TRÚC NHƯ MIDDLE
Nói bằng trigger -> hành vi -> guard -> query -> constraint -> side effects -> test.
Ví dụ: “Hai request chấm công cùng nhân viên được serialize bằng employee lock;
unique employee/day ở MySQL là bảo vệ cuối; lỗi phù hợp được controller chuyển thông báo;
audit/outbox ghi cùng transaction; sau commit mới xóa cache.”
Không chỉ nói “em có Repository Pattern” mà không chỉ ra code và trade-off.

THỰC HÀNH ĐỌC MỘT CÂU CODE:
  @repository = repository
Không phải copy database; chỉ gán object dependency vào instance variable.
  record = @repository.build(...)
Chưa insert. record là ActiveRecord object.
  authorize!(actor, record, :create?)
Không tạo record. Nó chỉ kiểm xem được tạo không.
  @repository.save!(record: record)
Đây mới đi tới model.save! và SQL insert/update tùy record.
  redirect_to attendances_path
Browser nhận redirect rồi gửi GET mới; không chạy view index trong cùng request create.
