2. MYSQL ĐANG LƯU NHỮNG GÌ?

companies
  id, code, name, active
  Công ty/workspace thật. Dữ liệu nghiệp vụ có company_id NOT NULL và FK.

users
  company_id, role, email, active, password_digest, ...
  role là mã vai trò trong company, ví dụ admin/hr/manager/employee/team_lead.
  Đã bỏ enum role cố định để có thể thêm vai trò trong database.
  FK tổng hợp (users.company_id, users.role) -> (company_roles.company_id, key).
  Database từ chối gán vai trò không tồn tại hoặc không thuộc company.
  Email đăng nhập vẫn unique toàn hệ thống, không đăng nhập mơ hồ theo company.

company_roles
  id, company_id, key, name
  Bốn vai trò khởi tạo: admin, hr, manager, employee.
  Có thể tạo thêm recruiter/team_lead/director ngay trên web/API.
  Cùng key của hai company là hai role rows độc lập, bộ quyền độc lập.

permissions
  id, key, name
  29 hành động hệ thống đã định nghĩa, ví dụ employees.read_all, leave.review.
  Danh mục hành động phải gắn với code xử lý; thêm một key tùy ý vào DB không
  tự tạo endpoint/tính năng mới. Người quản trị chọn quyền đã hỗ trợ.

role_permissions
  company_role_id, permission_id
  Liên kết N-N: vai trò nào có permission nào. Đây là nguồn grant thật.

user_permissions
  user_id, permission_id, granted
  granted=true: cấp thêm; granted=false: chặn riêng, ưu tiên hơn role grant.
  Không có row: kế thừa bộ quyền vai trò.

Công thức: quyền hiệu lực = quyền vai trò + cấp riêng - chặn riêng.
Company/user inactive thì không được dùng quyền dù grant rows vẫn còn.

PermissionCatalog chỉ cấp bộ quyền ban đầu khi tạo company.
Policy KHÔNG dùng catalog như bản clone của role->permission trong code.
Sau khi khởi tạo, đổi role_permissions/user_permissions trong MySQL là đổi
nguồn quyền mà User#allowed? đọc. Không có wildcard admin bỏ qua DB grant.

     Gửi các trường nhạy cảm trực tiếp cũng bị Command chặn.

Thay đổi quyền có tác dụng với request tiếp theo và token API đã cấp trước đó.

Bảo vệ tránh tự khóa hệ thống:

5. ĐỌC LUỒNG RUBY NHƯ BẠN ĐỌC LARAVEL

Ví dụ mở danh sách nhân viên:
  config/routes.rb draw module
  -> modules/workforce/config/routes/workforce.rb
  -> ApplicationController authenticate_user!
  -> Workforce::EmployeesController#index
  -> HrmWorkforce::Application::Queries::ListEmployees
  -> Hrm::UseCase.authorize! -> EmployeePolicy#index?
  -> User#allowed? đọc các bảng MySQL
  -> ActiveRecordReadRepository#employees
  -> Pundit.policy_scope!(actor, Employee)
  -> EmployeePolicy::Scope#resolve
  -> WHERE company_id=actor.company_id
  -> nếu không employees.read_all: thêm WHERE user_id=actor.id
  -> nạp Array + associations trước View -> ERB/JSON.

Ví dụ sửa quyền tài khoản:
  PATCH /manage/accounts/:id
  -> AdministrationController#save_account
  -> AdministrationRequest permit role/active/permission_overrides
  -> ManageCompanyAccess.call
  -> ActiveRecordAdministrationRepository#update_account!
  -> actor.allowed?("accounts.manage")
  -> khóa company để cập nhật quản trị nhất quán
  -> tìm User WHERE company_id=actor.company_id AND id=:id
  -> kiểm role tồn tại trong company, quyền hợp lệ, không tự khóa admin
  -> UPDATE users + thay user_permissions + INSERT audit_logs cùng transaction.

Tại sao Ruby controller ngắn hơn action Gate/company của Laravel DJI?
  Controller chỉ nhận HTTP và gọi UseCase.
  Base lo đăng nhập; UseCase/Policy lo quyền action + cùng company.
  Repository lo query scope + transaction. MySQL lo FK/unique cuối cùng.
  KHÔNG phải cứ include Pundit ở Base là mọi action tự có quyền đúng.

Company context thật:
  current_user.company / actor.company_id.
  Không cần tự viết CompanyContext.resolve! như ví dụ multi-membership cũ.
  company_id trong request body/query hoặc X-Company-ID không đổi tenant.
  Để tạo company mới và admin mới dùng provisioning CLI, không đổi user.company_id.

10. SQL ĐỌC ĐỂ TỰ KIỂM CHỨNG QUYỀN ĐANG NẰM TRONG MYSQL

Danh sách user + company + role:
  SELECT u.id,u.email,c.code AS company,u.role,r.name AS role_name
  FROM users u
  JOIN companies c ON c.id=u.company_id
  JOIN company_roles r ON r.company_id=u.company_id AND r.`key`=u.role;

Quyền theo vai trò:
  SELECT c.code,r.`key` AS role_key,p.`key` AS permission_key
  FROM company_roles r
  JOIN companies c ON c.id=r.company_id
  JOIN role_permissions rp ON rp.company_role_id=r.id
  JOIN permissions p ON p.id=rp.permission_id
  ORDER BY c.code,r.`key`,p.`key`;

Quyền cấp/chặn riêng:
  SELECT u.email,c.code,p.`key`,up.granted
  FROM user_permissions up
  JOIN users u ON u.id=up.user_id
  JOIN companies c ON c.id=u.company_id
  JOIN permissions p ON p.id=up.permission_id;

Các truy vấn trên là read-only. Thao tác sửa nên đi qua UI/API để được
validate quyền, bảo vệ admin, scope company và ghi audit atomically.
